## A. Open faults

### A1, a directory of "pending fixes" is a trap, SERIOUS

The directory was named as though it held a fix waiting to be applied, and a
read me inside it carried a ready made copy command that would overwrite the file
in use with the one in the directory.

**That command must not be run; it would take the code backwards.** Measured:

| | the "fixed" copy | the file in use |
|---|---|---|
| Date | 2026-08-09 16:48 | **2026-08-10 22:38** |
| Lines | 621 | **716** |
| the layer check, the H gate fix | present | **present** |
| the reference values file | **absent** | present |
| the stale reference verdict | **absent** | present |

The file in use is newer and a superset of the "fixed" copy: it already carries
the H gate fix and, on top of it, the stale reference fix added on 10 August. The
copy command would have deleted the second one.

The evidence was run twice, over seven scenarios:

- against the "fixed" module: **7 of 7 correct**, exit code 0
- against the file in use: **7 of 7 correct**, exit code 0

Scenario 1, which is a real output of that stage, gives an error under the old
logic and passes in both new versions, so the false alarm is gone. Scenarios 2,
3, 4, 6 and 7, which are a genuinely empty layer or one whose schema has shifted,
are still caught.

**What to do:** mark the directory as an archive rather than as something to
apply, and delete the copy command from its read me. It must not move into the
repository.

**A side finding:** the evidence script cannot be run again, because two dead
paths are embedded in it. A proof script that cannot repeat what it proves is not
a proof. Tests that go into the repository have to use paths relative to the
project root.

### A2, layer 2 looks only at LENGTH while layers 3 and 4 look at the TAXON, SERIOUS

> **A correction made the same day:** in the first round this finding was written
> as "the global scan counts unconditionally and the column name is wrong". That
> was wrong. `global_scan.py` is a **raw scanner**; its product field counting the
> total hits is the correct behaviour. The consumer makes the distinction, and the
> local layer had already fixed it on 2026-08-06: same length and off target are
> counted separately and only the off target count enters the verdict. The real
> gap is the narrower one below.

The four verification layers answer the question "does this product come from the
target itself or from outside it" **by different criteria**:

| The layer | The criterion | The source |
|---|---|---|
| 2, the local database | **length alone**, the expected value plus or minus a tolerance | the local layer |
| 3, MFEprimer | **the taxon**: inside the clade, outside the clade in the same domain, or a different domain | the clade classifier in the mfeprimer layer |
| 4, NCBI | **the taxon**, by organism exclusion in the Entrez query | `ncbi_layer.py` |

That the length criterion is unreliable had already been measured: of the 1,605
amplicons MFEprimer counted as off target, **95.7 per cent, that is 1,536, came
from inside the target's own clade** and differed only in length. The real cross
reaction was 0.9 per cent, that is 14 amplicons. Layer 3 was given a taxonomic
filter for that reason; **layer 2 was not.**

So the same mistake still stands in layer 2, and on group and universal primers
in particular the target's own length variants enter the verdict as off target.

**The data is there and is not being used.** Everything needed for a taxonomic
separation is on hand:

- The SILVA, UNITE and PR2 headers carry a full taxonomy, measured:
  `>AY846379.1.1791 Eukaryota;Archaeplastida;Chloroplastida;Chlorophyta;...`
- A target clade table holds the domain and clade tokens of every target across
  39 rows, and the clade classifier that reads it already works.
- The scanner already returns the header of every hit.

**The cap of 300, measured.** `global_scan.py` cuts the hit list at 300 records.
The product counter has no cap while the identifiers do. The real numbers from a
verification run:

| The target | All hits | Same length, the target itself | "Off target" |
|---|---:|---:|---:|
| Bacterial universal | 483,098 | 288,832 | **194,266** |
| Fungal universal, ITS and 18S | 159,382 | 152,166 | 7,216 |
| Microascaceae | 74,444 | 74,433 | 11 |
| Bacteroidales set | 71,945 | 71,925 | 20 |
| Fungal universal, the long operon | 57,408 | 56,520 | 888 |

**18 of the 22 targets exceed the cap.**

That table says two things:

1. **Removing the cap is the wrong fix.** The bacterial universal alone has 483
   thousand hits; at a 150 character header plus three integers each, that is
   about 100 MB. The scanner holds every candidate at once, loops over 12
   databases and writes a pickle at every chunk. Removing the cap would mean
   several GB of memory and bloated checkpoints, and it would break resilience
   against an interruption too.
2. **The right fix is to count, not to store.** A taxonomic separation does not
   need the list of identifiers; putting every hit into one of the four classes
   during the scan and incrementing a counter is enough. Memory then stays
   constant per candidate and the count is **complete**. The hit list can stay at
   300, where it already serves as a sample of the evidence.

Almost all of the bacterial universal's 194,266 "off target" hits are bacterial
16S, which for a universal bacterial primer is **on target by design**. That is
the same 95.7 per cent finding as before, in layer 2 and at a far larger scale.

**Why it was not applied in this round:** this fix changes the scientific
verdict, and some pairs would move from risky to clean. By the project's own rule
a change that moves a verdict is not made without a measurement to prove it and a
decision to accept it. There is also the warning in the earlier comment: once
layer 2 and layer 3 start asking **the same question**, the merge behaviour
changes. It has to be done as a separate step with a before and after table.

### A3, a hit threshold of 0 with no reasoning, WARNING

`verification/specificity_round.py`

```python
VURUS_ESIGI = 0   # a pair is risky when the off target product count is above this
```

A single hit produces a risky verdict. That may be a deliberate strictness,
consistent with the project's rule that not one wrong primer should reach an
order, but the reasoning is not written in the code. Since the rest of the
project writes the reasoning of every constant, this is the exception. In a
general purpose tool the value has to be settable by the user and the reason the
default is 0 has to be documented.

### A4, when the expected product length cannot be parsed, the layer drops silently, WARNING

`verification/mfeprimer_layer.py`

```python
try:
    bek[re.sub(r'\W+', '_', c['hedef'])] = (c['hedef'], int(c['urun']))
except (TypeError, ValueError, KeyError):
    pass
```

When the product value cannot be turned into a number, that target never enters
the expectation dictionary. The consequence: the parser cannot make the "same
length" distinction for that target and every product counts as off target. One
broken cell silently hardens the verdict of that row. It should at least print a
warning.

### A5, a typo in the hand filled NT template is swallowed silently, WARNING

`verification/specificity_round.py`

```python
try:
    out[r['hedef'].strip()] = dict(durum='TAMAM (elle)', hedef_disi=int(n), ...)
except ValueError:
    pass
```

If something that is not a number is written into the number field of the hand
filled template, for instance `~3` or `3 (maybe)`, then the NCBI layer never
comes into being for that target and the verdict table shows it as unknown. The
user believes the value was entered while the layer has dropped. This is exactly
the leading kind of fault the project itself defined: *the program produces the
wrong answer without raising an error.*

### A6, a broken `.fai` line silently corrupts the mean length, INFORMATION

`verification/identity_verification.py`. A broken line in the `.fai` index is
skipped while the totals keep accumulating, so the mean length is computed from
partial data. That value feeds the short list scoring. The effect is small but
silent.

### A7, the usage examples point at the mixed orientation directory, SERIOUS (documentation)

The docstring examples of the candidate generator and the group engine point at
the raw consensus directory.

That directory is **mixed in orientation**, measured at 71 antisense against 27
sense, and the configuration explicitly forbids reading it directly:

> in a reversed consensus an in-silico PCR **SILENTLY gives 0 products**, with a
> measured loss of 100 per cent

The code itself is right, since the path is taken as a CLI argument and is not
embedded. But a user following the documented example walks straight into the
trap. The examples have to be corrected to point at the canonical directory.

## The A2 measurement finished, and it STOPPED the change

Five databases carrying a taxonomy were scanned: SILVA SSU in 1,187 s, SILVA LSU
in 369 s, UNITE in 1,686 s, PR2 in 438 s and ROD in 460 s. 22 pairs, full
coverage.

### Finding 1, on the universal bacterial primer the taxonomy is plainly right

| The criterion | Bacterial universal |
|---|---:|
| "Off target" by LENGTH | **171,080** |
| By TAXON, foreign plus different domain | **122** |
| Inside the clade | 419,750 |
| Organelle | 4,726 |

419,750 of the 430,534 hits are bacterial, which for a universal bacterial primer
is **on target by design**. The length criterion counted 171,080 of them as off
target. The 95.7 per cent finding was confirmed at full scale.

The 4,726 chloroplast and mitochondrial hits are independent evidence that the
classifier works: organelle amplification by universal 16S primers is a known
problem, and the measurement found it by itself.

### Finding 2, on the other 21 targets the taxonomy cannot be used ON ITS OWN

| The target | LENGTH | TAXON |
|---|---:|---:|
| Microascaceae | 11 | **69,786** |
| Bacteroidales set | 20 | **43,546** |
| Fungal universal, ITS and 18S | 6,626 | 43,286 |
| Proteolytic Synergistaceae | 15 | 16,782 |
| Petrimonas genus | 0 | 651 |

69,786 real cross reactions for Microascaceae is impossible; for a pair that has
been ordered, that number is meaningless.

**The cause is in layer 2's own scan criterion and is already written in the
code:**

> This layer's criterion DOES NOT CARRY the last two bases condition at the 3'
> end, so it is LOOSER than the real PCR criterion

At most five mismatches and no 3' clamp condition. On a conserved marker gene
that criterion binds almost every record. **The length window of plus or minus 10
bp was working as an accidental strictness filter**, for the wrong reason, but it
was suppressing the noise.

The taxonomy answers "which clade does this belong to" correctly, but the raw
foreign count inherits the looseness of the scan. Putting the taxonomy in place
of length on its own would have drowned the verdict in risky.

### The decision: the verdict WAS NOT CHANGED

The taxonomic columns entered the report **as a diagnostic** and not into the
verdict. The right combination is taxonomy **plus** strictness, which the
MFEprimer layer already does through its Tm margin separating "can form" from
"cannot form".

**The next step, as separate work:** once a 3' clamp condition or a proximity to
the annealing temperature is added to layer 2, the taxonomic count can be tied to
the verdict. Not before.

This is where the rule of not changing anything without measuring it earned its
keep: the taxonomic separation was correct, but tied to the verdict on its own it
would have made 21 of the panel's 21 pairs unjustly risky.

## New: one installation gate, `install.sh`

The scattered installation scripts were gathered behind one gate.

```
bash install.sh status                 # measures, changes nothing
bash install.sh tools               # kraken2, bracken, minimap2, samtools, blast, seqkit
bash install.sh databases            # SILVA, PR2 and RefSeq, with instructions for UNITE and ROD
bash install.sh kraken-download          # a ready made Kraken2 database, fixed at k=35
bash install.sh kraken-build --kmer 31  # build your own database with your own k-mer
bash install.sh qiime                 # QIIME2, PICRUSt2 and the SILVA classifier
bash install.sh all
```

Three principles, derived from the project's own rules:

1. **A downloaded file is confirmed; the address is not trusted.** After every
   download the file is measured: is it really a FASTA, how many records, RNA or
   DNA. When the measurement does not hold, the file is marked suspect and **is
   not taken into use**. The minimum record counts come from real measurements,
   such as 510,495 for SILVA SSU and 2,069,189 for UNITE.
2. **Every step can be run again.** A confirmed file is skipped and a half
   finished download continues with `wget -c`.
3. **Nothing is skipped silently.** Everything that could not be installed is
   listed at the end and the exit code is not zero.

**Choosing the Kraken2 k-mer:** the ready made AWS databases are built with k=35
and l=31 and k cannot be chosen. If you want your own k, the database has to be
built from scratch. The script writes the build parameters into a file beside the
database, because `opts.k2d` is binary and which k it was built with cannot
otherwise be known six months later.

The k-mer section of the script says plainly that **choosing a k-mer does not on
its own solve the identity problem**. The cause of the Kraken divergence is not k
but the LCA itself and the coverage of the database. Whatever k it is built with,
identity claims have to be tested independently by the identity verification.

**A fault found along the way:** the status command reported `kraken2`, `bracken`
and `seqkit` as missing in its first version. All three **were installed**, in a
micromamba environment, and were not on `PATH` while that environment was
inactive. A check that looks only at `PATH` makes a correctly installed system
look broken. The environment is searched too now and where a tool was found is
written down. The version flag is also chosen per tool, since the wrong flag was
producing meaningless lines.

## F. Two faults found in the identity verification

### F1, unnamed environmental records were counted as a SPECIES name, SERIOUS

`verification/identity_verification.py`, in the name resolver.

Sets like NCBI nt are full of unnamed records. The resolver's second regular
expression took them for a binomial. Run live and measured:

```
'KJ734864.1 Uncultured prokaryote clone D5...'  ->  genus='Uncultured', species='Uncultured prokaryote'
'GQ503828.1 Bacterium enrichment culture...'    ->  genus='Bacterium',  species='Bacterium enrichment'
```

Because the identity was 99 per cent, the defensible level function counted that
as a name at species level and the claim was stamped CONFIRMED. So having no
answer was being reported as a confirmed identity. **4 of the 12 claims** were in
that state.

The trap was already known in the project and was filtered in two other places,
and the NCBI layer's docstring documents it. It was missing in the one module
**responsible** for naming, which had zero matches for "uncultured".

**Fixed.** An unnamed record no longer produces a name, and a separate verdict
branch was added for a reference that cannot be named. The existing "no name can
be given" branch gave its reason as "the identity is below the genus threshold",
while the identity here is 99 per cent. A wrong reason pushes the reader towards
"a better reference would give a name"; the problem is not how close the
reference is but that it has no name.

Not letting the filter grow too wide is critical, since silencing real names
would be the more insidious fault. The dedicated test covers both directions,
12 of 12: unnamed records are dropped while *Petrimonas sulfuriphila*,
*Methanosarcina mazei* and *Bacteroides fragilis* still resolve intact.

**The measured effect:** the proposed name dropped in 4 of the 12 claims.

| No | The verdict | Before | After |
|---|---|---|---|
| 4 | CONFIRMED | SPECIES / *Uncultured prokaryote* | CANNOT BE NAMED |
| 5 | TO BE CORRECTED | SPECIES / *Uncultured bacterium* | CANNOT BE NAMED |
| 6 | CONFIRMED | SPECIES / *Bacterium enrichment* | CANNOT BE NAMED |
| 12 | TO BE CORRECTED | SPECIES / *Uncultured bacterium* | CANNOT BE NAMED |

The other 8 claims were untouched: *Petriella setifera*, *Petrimonas* sp. and
*Methanosarcina mazei* rest on real named references.

### F2, the checkpoint was caching the DERIVED VERDICT, SERIOUS

This surfaced after F1 was fixed, and it is the deeper defect.

With the F1 fix in place the round was run again: it finished in 20 seconds with
exit code 0 and said "12 of 12 taken from the previous run". Comparing before and
after, **all 12 rows were identical.** The fix had never run.

The cause: the claim checkpoint stored the **whole** claim, the naming and the
verdict included, while the settings signature seals only the **scan**
parameters. The consequence: a fix in the verdict logic is silently ignored on a
rerun and the old verdict comes back.

This is the most harmful form of the stale checkpoint class the auditor itself
flagged, 2,899 of 3,011: *you believe the fix has been applied.*

**Fixed, with an architectural separation:**

- The naming block was pulled out into its own function, so a fresh run and a
  re-derivation use **the same code**. (In this code base the fault of "two
  versions of the same check disagreeing" has already been measured twice,
  finding B and one other. A third was not opened.)
- The checkpoint now also stores the **raw hits**.
- When the raw measurement is there, **the scan is skipped but the verdict is
  derived again**.
- An old format checkpoint is not accepted silently: it says that there are no
  raw hits, that the verdict cannot be re-derived, and that it is rescanning.

The principle: **the scan is what is expensive, in hours, while the verdict is a
derivation that takes seconds. The derivation has to be redone on every run.**

The measured result: a rerun now says the scan came from the cache and the
verdict was derived again, and it takes seconds. 223 scan caches and 8 NCBI
records were kept.

### F3, the nearest 5 organisms were added

Raised from the first 3 to 5 on request. Three design decisions:

1. **Deduplication by organism.** The pool holds hits from 13 databases and the
   same species is in most of the sets; without deduplication the "nearest 5"
   would easily have been 5 records of the same organism.
2. **An unnamed record is not printed as a dash.** If what was matched cannot be
   seen, the reader takes a 99 per cent row seriously without a second thought.
   The record's own description is now written with an "unnamed" prefix.
3. **"Unnamed" and "not resolved to species" were separated.** SILVA records
   carry a full taxonomy but may have no species binomial; calling those unnamed
   would put a classified record in the same basket as an environmental clone.
   The deepest taxonomic token is written instead, as in
   `uncultured bacterium (Petrimonas)` and `Synergist (Synergistales)`.

An example, claim 4, after the fix:

```
1) unnamed: Uncultured prokaryote clone A13 16S...  99.00%  [NCBI nt]
2) Methanosarcina vacuolata                         97.57%  [RefSeq archaea 16S]
3) Methanosarcina barkeri                           97.40%  [RefSeq archaea 16S]
4) Methanosarcina mangrovi                          97.35%  [RefSeq archaea 16S]
5) Methanosarcina siciliae                          97.27%  [RefSeq archaea 16S]
```

That table also confirms the claim itself: the claim said 97.6 per cent to
*M. vacuolata* and the measurement gives 97.57.

## A note on method

A1 was recorded in the first round as "the fix has not been applied", and the
only basis was that a `diff` returned a difference. That was an insufficient
inference: two files also look different when one is a superset of the other.
Once the date, the line count and the presence of each feature were measured, the
conclusion reversed. Every audit rule that goes into the repository has to pass
the same test: *there is a difference* and *something is missing* are not the same
thing.

## What the rename broke, 2026-08-22

While the directory and file names were being turned into English, some imports
stayed on the old name. All of them were valid syntax and passed every check that
reads the file as text; the fault appeared only when the module was **imported**.

- `screening/__main__.py` still imported four modules under their Turkish names,
  which are now `geometry.py`, `targets.py`, `generator.py` and `sample.py`.
  Because every key in the menu goes through that module, **not one of them
  worked**. Nine more files in the package were in the same state, and three
  modules under `engine/` were importing the gateway under its old name.
- `steps/specificity.py` imported `alignment` at the top and used the old name
  four lines below. Because the name was bound nowhere, the module fell over with
  a `NameError`, and since `steps/regression_test.py` loads that file the whole
  regression suite could not run either. After the fix 137 of 137 items pass.
- The same three modules under `engine/` assumed the project root was a path
  under `/tmp` and wrote their output there. The root is now derived from the
  file's own location, the output goes under the results directory, and an
  environment variable still overrides it. Three shell scripts also carried one
  person's desktop path; two were usage examples and one was running code that
  silently measured nothing on any other machine.

Three checks were added to `tests/test_repo_health.py` so that this class is not
missed again: that a relative import names a real module, that every name used is
bound somewhere, and that no machine specific absolute path is present. The list
of modules imported for their side effects also gained the menu entry point and
the stages its driver runs; the reason the first breakage went unnoticed is that
they were not on that list.

## `cross_check.py` was not passing its own test, 2026-08-22

The self test gives every module a deliberately broken input and expects the
matching finding code to come out. For a while 5 of the 7 modules were passing.

- **Internal consistency** crashed before it could compare anything. With no
  panel workbook at the root, the source stayed `None` and the sheet reader
  called `os.path.exists(None)` and raised a `TypeError`. A missing file is not a
  crash but a missing source: it now reports the missing file and the module
  carries on.
- **Taxon coverage** could not see a status line written in English. Whether a
  row counted as "not achieved" was decided by a pattern that recognised Turkish
  wording alone, while the line the test seeds is
  `**Not achieved.** No reason recorded`. That pattern and the four category
  patterns now recognise both languages.

In the same round two arguments of one finding message had swapped places: the
sentence was reordered when it was translated into English and the arguments were
not, so the name of the file the column should have been in was printed as the
column name.

The test now gives 7 of 7.
